```text
需求文档：奥克斯老款空调“一键预设”Android 红外遥控 App

========================================
1. 项目背景与目标
========================================

现状：用户使用小米手机，通过“万能遥控”App 控制一台非智能老款奥克斯空调（纯红外遥控，无 Wi-Fi）。每次睡前需要手动执行多步操作：打开 App → 开机 → 设睡眠模式 → 调温度 → 设定时关机，步骤繁琐。

目标：开发一款 Android App，用户打开 App、手机对准空调，一键将空调设置为预设状态（开机 + 睡眠模式 + 指定温度 + 定时关闭）。

核心约束：空调为单向红外设备，App 只能发送指令，无法获取空调是否执行成功的反馈。这是开环控制，需在设计与预期管理中明确接受。


========================================
2. 用户场景
========================================

1. 用户睡前拿起手机，打开本 App。
2. 手机红外发射口对准空调。
3. 点击预设按钮（如“睡眠 26℃ 2 小时后关”）。
4. App 依次发射对应的红外指令（开机、睡眠模式、温度、定时关机）。
5. 用户听到空调“嘀”声即视为操作完成（App 本身无法确认）。


========================================
3. 功能需求
========================================

3.1 核心功能（MVP）

F1 红外硬件检测：启动时检查手机是否有红外发射器（ConsumerIrManager.hasIrEmitter()），无则提示不支持。
F2 一键预设发射：点击按钮后，按正确顺序发射一组红外指令，完成“开机 + 睡眠模式 + 温度 + 定时关机”。
F3 多预设管理：支持保存多个预设（不同温度/定时组合），用户可选择发射。
F4 对准引导：界面提示用户将手机红外口对准空调。

3.2 可选功能（后续迭代）

- 预设编辑（自定义温度、定时时长）
- 发射历史记录
- 定时自动发射（需权衡 Android 后台限制，可靠性有限）

3.3 明确不做 / 做不到

- 无法确认空调是否执行成功（红外单向通信，无回传）
- 无法读取空调当前状态（开关、温度、模式均不可知）
- 不依赖“万能遥控”App 的数据导出（其数据私有且格式不兼容）


========================================
4. 技术方案
========================================

4.1 技术栈

语言：Kotlin（Android 原生）
最低 API：19（ConsumerIrManager 自 Android 4.4 引入）
核心 API：android.hardware.ConsumerIrManager.transmit(frequency, pattern)

4.2 权限与声明

<uses-permission android:name="android.permission.TRANSMIT_IR" />
<uses-feature android:name="android.hardware.consumerir" android:required="false" />

TRANSMIT_IR 为普通权限，安装即授予，无需动态申请。

4.3 核心代码结构

val irManager = getSystemService(Context.CONSUMER_IR_SERVICE) as? ConsumerIrManager
if (irManager?.hasIrEmitter() != true) { /* 提示无红外 */ return }

val frequency = 38000 // 38kHz 载波
val pattern: IntArray = /* 奥克斯真实脉冲时序，单位微秒 */
irManager.transmit(frequency, pattern)

限制：单次 pattern 总时长必须小于 2 秒，否则系统拒绝发射。

4.4 关键难点：获取奥克斯红外编码数据

这是项目真正的门槛。现成可直接用于 Android IntArray 的奥克斯码库基本找不到，可行路径如下：

路径 A（推荐）：移植 IRremoteESP8266 的 Electra 协议编码逻辑
- 有实测确认奥克斯 YKR 系列遥控器使用 Electra 协议（ELECTRA_AC），帧结构 13 字节，包含开关、模式、温度、风速完整状态，载波 38kHz。
- 用 Kotlin 重写该协议的状态编码逻辑，根据“模式/温度/开关”实时生成字节，再转换为 38kHz 脉冲时序 IntArray。
- 优点：不依赖抓取波形，可编程生成任意状态组合。

路径 B：物理抓取波形（最可靠的数据来源）
- 用带学习功能的红外接收模块（几十元）配合 Arduino 或逻辑分析仪，对着奥克斯原装遥控器抓取各按键波形，转成微秒数组。
- 缺点：需硬件与动手能力；需分别抓取“开机”“睡眠”“温度”“定时”等多条指令并确定发射顺序。

路径 C：参考开源项目
- pyhvac（Python，声明支持奥克斯型号）、AC-Nexus（面向博联硬件，码库格式不兼容）等仅可作协议验证参考，无法直接复用。

已排除的路径：从“万能遥控”App 提取数据——其数据存于私有目录，需 Root 且可能加密/混淆，格式与 IntArray 不兼容，成本高、不确定性大。

4.5 指令组合策略

空调红外协议通常是状态码（发送完整状态）而非独立“按键码”。需明确：
- 若抓取/生成的指令本身已包含“定时关机”状态，则一次发射即可；
- 否则需按顺序发射多条指令（开机 → 睡眠 → 温度 → 定时），并注意指令间的时间间隔与空调接收时序。


========================================
5. 风险与限制
========================================

无法确认执行结果：红外单向，App 不知空调是否收到。应对：界面明确提示“请对准空调，听到嘀声即成功”。
编码数据获取难：无现成 Android 码库。应对：优先移植 Electra 协议逻辑，或物理抓取波形。
指令顺序/时序错误：多条指令连发可能被空调忽略。应对：需实测调整指令间隔。
后台定时不可靠：Android Doze 限制精确唤醒。应对：MVP 不做后台自动发射，仅做“打开 App 一键发射”。
机型兼容性：奥克斯不同型号协议可能有差异。应对：以用户实际空调遥控器抓取/实测为准。


========================================
6. 开发里程碑
========================================

M1 硬件验证：写最小 Kotlin 程序，确认 hasIrEmitter() 为 true，发射任意短数组并用摄像头验证红外光输出。
M2 数据获取：完成 Electra 协议逻辑移植，或抓取奥克斯遥控器完整波形，得到可用的 IntArray。
M3 单指令验证：用 App 发射“开机”指令，实测空调响应。
M4 组合指令：实现“开机 + 睡眠 + 温度 + 定时”顺序发射，实测成功率。
M5 预设管理：完成多预设保存与一键发射界面。


========================================
7. 验收标准
========================================

- App 在无红外硬件的手机上能正确提示不支持。
- 在有红外的手机上，对准奥克斯空调点击预设按钮，空调能进入预设状态（以听到“嘀”声并观察到实际运行为准）。
- 预设可保存、可选择、可重复发射。
- 界面明确告知用户“无法确认执行结果，需对准空调”。
```
