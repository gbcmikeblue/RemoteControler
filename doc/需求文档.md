## 1. 产品概述

### 1.1 一句话定义

一款面向**非智能红外空调**的 Android 工具：打开 App、手机对准空调、点一下，就把空调置为预设状态（模式 + 温度 + 风速 + 静音 + 运行时长），到点自动关机。

### 1.2 目标用户

| 用户类型 | 特征 | 关注点 |
|---|---|---|
| **主要用户**：睡前使用空调的家庭成员 | 每晚固定流程：开机→低温→静音→定时关 | 一步到位、不要多点、不要记参数 |
| **次要用户**：多场景使用者 | 白天制冷、夜间睡眠、不同时长组合 | 多个预设可保存、可快速切换 |
| **边缘用户**：有红外手机的其他品牌用户 | 空调品牌不是奥克斯 | 能否通过换载波/换协议适配 |

> 产品定位为**个人工具型单机 App**，不面向应用商店分发（影响：`USE_EXACT_ALARM` 等受限权限可放心使用）。

### 1.3 核心使用场景

| 编号 | 场景 | 触发 | 期望结果 |
|---|---|---|---|
| S1 | **睡前一键预设**（主场景） | 躺下前拿起手机点一下 | 空调进入「制冷 26℃ + 静音」并开始计时，2 小时后自动关机 |
| S2 | 自定义预设 | 周末想用 24℃ / 3 小时 | 新建一条预设，之后和 S1 一样一键调用 |
| S3 | 试出可用载波 | 新机型/换手机，不确定 38kHz 是否可用 | 逐个试 36/38/40kHz，有反应的记为成功记录 |
| S4 | 由成功频率生成预设 | 试出 40kHz 可用 | 把该频率固化为预设，后续直接用 |
| S5 | 定时到点自动关机 | App 已退出、手机锁屏 | 到点自动发关机指令，无需人操作 |

### 1.4 主要功能边界

**做**

- 发射红外指令控制空调（单向）
- 多预设本地保存与一键执行
- 按运行时长自动关机（系统闹钟）
- 载波频率测试与成功记录

**明确不做**

| 不做项 | 原因 |
|---|---|
| 读取空调当前状态（开关/温度/模式） | 红外单向通信，物理上无法回读 |
| 确认指令是否被执行 | 同上；只能靠用户听「嘀」声 |
| 控制 Wi-Fi / 智能空调 | 超出红外工具定位 |
| 读取「万能遥控」App 的配置 | 已实测：私有目录受沙箱保护，非 root 不可读（见第 6 节 Q9） |
| 学习遥控器波形（App 内置） | 手机只有发射器，没有红外接收头，硬件上做不到 |
| 后台常驻服务 | 无必要，定时用系统闹钟即可 |
| 云端同步 / 账号体系 | 单机工具，无服务端 |

## 3. 模块详细需求

### M1 红外硬件检测与发射【核心】

| 编号 | 需求 | 输入 | 预期行为 | 状态 |
|---|---|---|---|---|
| M1-1 | 启动时检测红外发射器 | 无 | `hasIrEmitter()` 为 false 时，主界面明确提示"本机没有红外发射器"并禁用发射入口 | 已实现 |
| M1-2 | 列出硬件支持的载波 | 无 | 读取 `getCarrierFrequencies()`，在主界面展示（如 30/33/36/38/40/56kHz） | 已实现 |
| M1-3 | 发射前校验脉冲序列 | `IntArray` | 序列为空、非成对、含非正数、总时长 > 2 秒时，拒绝发射并给出原因 | 已实现 |
| M1-4 | 发射失败要可感知 | 发射结果 | 失败时界面显示失败原因，不再静默 | 已实现 |
| M1-5 | 发射在后台线程执行 | — | 不阻塞 UI，发射期间禁用重复点击 | 已实现 |

**权限要求**：`TRANSMIT_IR`（normal，安装即授予）、`uses-feature android.hardware.consumerir required=false`（无红外机型也能安装）。

### M2 Electra 协议编码【核心】

| 编号 | 需求 | 说明 | 状态 |
|---|---|---|---|
| M2-1 | 13 字节状态帧 | 首字节固定 `0xC3`，末字节为校验 | 已实现 |
| M2-2 | 校验算法 | 前 12 字节**算术累加和**（低 8 位） | 已实现 |
| M2-3 | 位序 | 字节内 **LSB 先发** | 已实现 |
| M2-4 | 帧结构 | **单帧 104 bit 连续发送，不分段**；脉冲序列 = header + 104 bit + footer | 已实现 |
| M2-5 | 时序 | 38kHz；header 9166/4470µs；bit 646µs；逻辑 1 间隔 1647µs、逻辑 0 间隔 547µs | 已实现 |
| M2-6 | 字段编码 | 电源 byte9 bit5；模式 byte6 bits5-7；温度 byte1 bits3-7（偏移 8）；风速 byte4 bits5-7；摆风 byte1 bits0-2 / byte2 bits5-7；静音 byte5 bit7 | 已实现 |
| M2-7 | 可验证性 | 存在与真实抓帧逐字节比对的自动化用例 | 已实现 |

**验收基准帧**（IRremoteESP8266 仓库真实抓取）：
`C3 6F E0 00 A0 00 28 64 00 20 00 1E 7C`

**协议能力缺口**（影响 M5、M7）：

- 没有独立「睡眠」字段 → 用 Quiet（静音）近似
- 没有「定时关机」码 → 必须由手机侧计时

### M5 定时关机（运行时长）【核心】

| 编号 | 需求 | 说明 | 状态 |
|---|---|---|---|
| M5-1 | 语义 | 「运行 N 小时后关机」，不是「在某个时刻关机」 | 已实现 |
| M5-2 | 粒度与范围 | 30 分钟一档，0.5 ~ 12 小时（0 = 不启用） | 已实现 |
| M5-3 | 触发方式 | 系统精确闹钟（`AlarmManager` + `RTC_WAKEUP`），**App 退出/锁屏仍可触发** | 已实现 |
| M5-4 | 到点动作 | 后台发一帧「关机」状态（保留原温度/模式） | 已实现 |
| M5-5 | 权限与降级 | 优先精确闹钟；系统不允许时退化为非精确，并给出「去授权」入口 | 已实现 |
| M5-6 | 重复登记 | 再次执行带定时的预设会覆盖上一个定时；执行不带定时的预设会取消定时 | 已实现 |
| M5-7 | 到点提醒 | 是否通知用户"已自动关机" | **未实现，待确认 Q5** |

**已知限制**

- 用户手动「强行停止」App 会清空系统闹钟（Android 行为）；
- 手机关机/电量耗尽期间不会触发；
- 手机时间被手动修改会影响触发时刻。

## 4. 数据模型

```
Preset
├── id            Long
├── name          String
├── carrierFreqHz Int          默认 38000
├── state         ElectraState
└── rawCommands   List<IntArray>  为空 = 使用协议编码

ElectraState
├── power              Boolean
├── mode               AUTO / COOL / DRY / HEAT / FAN
├── temperature        16..32
├── fan                AUTO / LOW / MEDIUM / HIGH
├── swingVertical      Boolean
├── swingHorizontal    Boolean
├── quiet              Boolean        ← 近似「睡眠」
├── turbo / iFeel / clean  Boolean    （协议支持，UI 未暴露）
├── lightToggle        Int
├── sensorTemperature  Int?
└── autoOffMinutes     0..720，0 = 不定时
```

**存储**：SharedPreferences + JSON，键 `aircon_presets` / `aircon_frequency_records`。

## 6. 歧义 / 冲突 / 缺口清单

| 编号 | 类型 | 问题 | 影响 | 建议 |
|---|---|---|---|---|
| **Q1** | 冲突 | v1 要求「睡眠模式」，但 Electra 协议**没有睡眠字段**。当前用「静音（Quiet）」近似 | 用户对"睡眠"的预期可能与静音不等价 | 确认是否接受静音近似；或改用 I-Feel / Turbo 组合 |
| **Q2** ✅已定稿 | 冲突 | v1 与旧代码写温度 16–30℃，Electra 协议位宽支持 **16–32℃** | — | **已确认：UI 与编码统一收敛到 16–30℃**（2026-10-31） |
| **Q3** ✅已修复 | 缺失 | App **无法关机**：预设编辑页固定 `power = true`，没有"关闭空调"入口 | — | **已确认并实现**：主界面「工具」区新增「关闭空调」按钮，沿用最近预设的温度/模式/风速，只清电源位，并撤销已登记的定时 |
| **Q4** | 冲突 | v1 要求"依次发射 开机→睡眠→温度→定时"四帧；状态码协议正确做法是**发一帧完整状态** | 多帧反而可能被空调丢弃 | 确认采用单帧；若某机型必须多帧，改用 `rawCommands` |
| **Q5** | 缺失 | 定时到点自动关机后，**没有任何通知** | 用户不知道是否执行成功 | 建议加一条通知（需 `POST_NOTIFICATIONS` 权限） |
| **Q6** | 不完整 | 原始波形导入界面形态未定 | 无法开始实现 M9 | 确认：粘贴文本框 / 文件导入 / 二维码 |
| **Q7** | 不完整 | 预设数量上限、排序规则、置顶能力未定义 | 预设多了不好用 | 建议：上限 20 条，支持置顶 |
| **Q8** | 风险 | DEBUG 自检入口写在 `src/main`，靠 `BuildConfig.DEBUG` 屏蔽 | 发布包虽不触发，但代码仍在 | 确认是否迁到 `src/debug/` 源集 |
| **Q9** | 已排除 | 曾计划"读取万能遥控 App 配置" | 实测：私有目录沙箱保护，非 root 不可读 | 已从代码删除，确认不再需要 |
| **Q10** | 不完整 | 多台空调 / 多个房间的场景未定义 | 当前只有一份预设集 | 确认是否需要"设备"概念 |
| **Q11** | 不完整 | 由频率记录生成预设时，温度/模式被固定写成「制冷 26℃ 静音」 | 用户可能想要别的组合 | 确认是否改为跳转编辑页让用户填 |
| **Q12** | 冲突 | 需求写"支持多预设（不同温度/定时组合）"，但预设里 **载波频率** 也可不同 | 用户可能不理解为什么同品牌要存多个频率 | 确认是否在 UI 上隐藏载波，统一用 38kHz |
| **Q13** | 不完整 | 应用名称、图标、是否多语言未定义 | 影响发布形态 | 确认 |
